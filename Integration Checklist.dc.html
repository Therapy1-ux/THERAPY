Integration checklist — Momence and each wearable.

Everything the portal currently mocks, broken into build-ready steps. Each block is independently shippable; order shown is the recommended sequence.

1 · Momence (booking, membership, payments)

Highest priority

Momence stays the single commerce backend. The portal reads from it — never a second source of truth.

Request API access from Momence
Apply for API credentials via Momence support (business plan required). Confirm access to Appointments, Memberships, Customers and Payments endpoints.
Access
Map Momence customer ID → THERAPY account
Momence customer record becomes the account spine. Store momence_customer_id on your member table; never duplicate names/emails as a second truth.
Schema
OAuth / API-key server-side proxy
Keys live server-side only. A thin API layer (e.g. /api/momence/*) proxies reads so the portal never holds credentials.
Auth
Sync bookings (read)
Poll or webhook upcoming/past appointments per member; render in portal “Sessions” instead of the current mock. Cache with 5-min TTL.
Bookings
Sync membership tier + credits (read)
Pull active membership, level, remaining session credits, renewal date. Drives tier-gated portal features.
Membership
Webhooks for changes
Subscribe to booking created/cancelled and membership changed events; update the local cache so the portal is live, not stale.
Webhooks

Booking/purchase actions keep sending members to the hosted Momence flow (existing URLs). No custom checkout.

2 · Wearables — shared foundation first

Use one aggregator (Terra or Spike) rather than four native integrations — one webhook, one normalised schema, all four devices. Native OAuth per device is the fallback if aggregator pricing fails.

Choose aggregator: Terra vs Spike
Compare per-user pricing, device coverage (Whoop, Oura, Garmin, Apple Health all supported by both) and webhook reliability. Decision gate for everything below.
Decision
Provision aggregator account + sandbox
Create dev + prod environments, register redirect URLs for the portal domain.
Access
Normalised metrics schema
One table: member_id, source, metric (hrv, rhr, sleep_score, recovery, steps, spo2), value, recorded_at. All four devices write to it identically.
Schema
Webhook ingestion endpoint
Single endpoint receives daily/intraday payloads, validates signature, upserts into the metrics table. Idempotent — devices resend.
Ingestion
Connect/disconnect UI wiring
The portal’s existing connect cards call the aggregator’s widget/auth URL per provider; store connection status + last-sync timestamp per device.
Portal
Backfill on first connect
Request 90 days of history when a member first links a device, so My Plan cross-references have data from day one.
Data

Whoop

via aggregator
Key metrics: recovery %, strain, HRV, resting HR, sleep performance
Enable Whoop in aggregator dashboard
Test OAuth consent flow with a real Whoop account
Map recovery % → portal readiness dial
Verify daily webhook arrives ~6–8am local
QA: token refresh after 30-day expiry
Gotcha: Whoop has no steps count — hide the steps tile for Whoop-only members.

Oura

via aggregator
Key metrics: readiness, sleep score, HRV, body temp deviation, resting HR
Enable Oura in aggregator dashboard
Test consent with Gen3/Gen4 ring account
Map readiness score → portal readiness dial
Ingest temperature deviation (flag for illness/cycle insights)
QA: member revokes access from Oura app — handle disconnect webhook
Gotcha: Free-tier Oura accounts return limited data; note the Oura membership requirement in the connect card.

Garmin

via aggregator
Key metrics: HRV (overnight), body battery, stress, steps, VO₂ max estimate
Enable Garmin Health in aggregator (requires Garmin approval, ~1–2 weeks)
Test consent via Garmin Connect login
Map body battery → energy tile; VO₂ max → performance panel
Handle multi-device Garmin accounts (watch + scale)
QA: historic backfill is limited — document the gap
Gotcha: Garmin’s production API approval is the slowest of the four — apply first, build last.

Apple Health

aggregator SDK / iOS only
Key metrics: HRV, resting HR, sleep stages, steps, workouts (aggregated from iPhone + Watch)
Confirm aggregator’s Apple Health path (requires their mobile SDK or an iOS companion shortcut — no server-to-server API exists)
Decide: PWA limitation notice vs lightweight iOS shell app
Request only needed HealthKit scopes (HRV, HR, sleep, steps)
Test background delivery frequency on real device
QA: data continues after phone restart / app kill
Gotcha: Apple Health cannot sync server-side. Without an iOS app in some form, this stays manual — set expectations in the connect card now.

3 · Cross-cutting (required before launch)

Account auth for the portal
Email magic-link or Momence SSO. One login = one member = one health memory.
Auth
Database + file storage
Postgres (members, metrics, records) + object storage for bloodwork PDFs/scans with per-member access rules. Serves the portal upload zones.
Infra
Privacy & consent
Health data consent screen at connect time, Australian Privacy Principles (APP) compliance review, data-deletion path when a member leaves.
Legal
Practitioner view permissions
Role-based access: members see their own memory; practitioners see assigned members only; audit log on every record view.
Access
Monitoring
Alert on webhook failures and stale syncs (device silent > 48h) so “connected” never silently means “broken”.
Ops

Sequence rationale: Momence first (it's the account spine — every member already exists there), then the aggregator foundation, then devices in order of member demand. Bloodwork/scan upload storage rides on the same auth + database from step 1.
